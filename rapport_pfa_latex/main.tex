\chapter*{Résumé}
\addcontentsline{toc}{chapter}{Résumé}

Ce rapport présente la conception et la réalisation de \textbf{AACA} (\textit{AI Academic Cognitive Assistant}), une application mobile intelligente visant à aider les étudiants à mieux organiser, comprendre et réviser leurs cours. Le principe est le suivant : l'étudiant capture une photo de ses notes ou d'un tableau, et l'application extrait automatiquement le contenu, le structure, puis génère des supports pédagogiques tels qu'un résumé, des quiz et des flashcards.

Le système repose sur une architecture client-serveur. L'application mobile est développée avec \textbf{React Native} et \textbf{Expo}, tandis que le backend est construit avec \textbf{FastAPI} en Python. Les données sont stockées dans \textbf{MongoDB}. Le traitement combine des modules d'OCR multi-moteur (PaddleOCR, EasyOCR, Tesseract), un service d'extraction de formules mathématiques (pix2tex), et des modèles de langage (LLM) pour la génération de contenu. Une recherche sémantique basée sur des embeddings et une base vectorielle (ChromaDB) permet à l'étudiant d'interroger ses notes via un assistant questions/réponses.

Le projet met également l'accent sur l'apprentissage actif grâce à la révision espacée par l'algorithme SM-2, l'apprentissage adaptatif et un tableau de bord de progression. Un flux multi-photos permet de capturer plusieurs pages d'un même cours et de les fusionner en une seule note structurée.

\textbf{Mots-clés :} intelligence artificielle, OCR, application mobile, répétition espacée, FastAPI, React Native, MongoDB, flashcards, RAG.

\chapter*{Abstract}
\addcontentsline{toc}{chapter}{Abstract}

This report presents the design and implementation of \textbf{AACA} (\textit{AI Academic Cognitive Assistant}), an intelligent mobile application aimed at helping students better organize, understand, and review their courses. The core idea is simple: the student captures a photo of handwritten notes or a whiteboard, and the application automatically extracts the content, structures it, and generates learning materials such as summaries, quizzes, and flashcards.

The system follows a client-server architecture. The mobile application is built with \textbf{React Native} and \textbf{Expo}, while the backend is developed with \textbf{FastAPI} in Python. Data is stored in \textbf{MongoDB}. The processing pipeline combines multi-engine OCR (PaddleOCR, EasyOCR, Tesseract), a mathematical formula extraction service (pix2tex), and large language models for content generation. Semantic search based on embeddings and a vector store (ChromaDB) enables a question-answering assistant over the student's notes.

The project also emphasizes active learning through spaced repetition using the SM-2 algorithm, adaptive difficulty adjustment, and a progress dashboard. A multi-photo session flow allows students to photograph multiple pages of the same lecture and merge them into a single structured note.

\textbf{Keywords:} artificial intelligence, OCR, mobile application, spaced repetition, FastAPI, React Native, MongoDB, flashcards, RAG.

\chapter*{Introduction générale}

\section*{Contexte}

L'apprentissage universitaire repose encore largement sur des méthodes traditionnelles : prise de notes manuelle, capture de tableaux, relecture de documents et préparation individuelle de résumés. Ces pratiques restent utiles, mais elles deviennent difficiles à gérer lorsque le volume de cours augmente. Les étudiants accumulent des photos, des fichiers et des notes dispersées, sans disposer d'un outil capable de transformer automatiquement ces contenus bruts en supports de révision actifs.

En parallèle, les progrès récents de l'intelligence artificielle ont rendu possible l'analyse automatique d'images, l'extraction de texte, la compréhension de contenus académiques et la génération de ressources pédagogiques. Les moteurs d'OCR permettent d'extraire du texte depuis des images de qualité variable, tandis que les grands modèles de langage peuvent reformuler, synthétiser et générer des questions à partir d'un contenu donné.

\section*{Problématique}

La problématique centrale est la suivante : \textit{comment concevoir une application mobile capable de transformer automatiquement une capture de notes académiques en ressources d'apprentissage structurées, interactives et personnalisées ?}

\section*{Objectifs}

Le projet \textbf{AACA} propose de centraliser dans une seule application la chaîne complète allant de la capture d'une photo au suivi de la progression de l'étudiant : extraction et correction du texte, classification automatique de la matière, génération de résumé, de quiz et de flashcards, révision espacée et assistant questions/réponses sur les notes.

\section*{Organisation du rapport}

Le présent rapport est structuré en trois chapitres. Le premier présente le contexte, la problématique et l'analyse des besoins. Le deuxième décrit la conception du système, l'architecture retenue et les choix technologiques. Le troisième expose la réalisation concrète de l'application, les tests effectués ainsi que les limites et les perspectives d'amélioration.

\chapter{Contexte général et analyse des besoins}

\section{Introduction}

Ce chapitre présente le cadre général du projet AACA. Il expose les difficultés rencontrées par les étudiants dans l'organisation et la révision de leurs cours, formule la problématique centrale, identifie les besoins fonctionnels et non fonctionnels, et fournit une analyse comparative des solutions existantes.

\section{Contexte du projet}

\subsection{Évolution des pratiques d'apprentissage}

Dans l'environnement universitaire actuel, les étudiants manipulent une quantité importante d'informations : cours magistraux, travaux dirigés, supports PDF, notes personnelles, schémas, formules et photos de tableaux. Une pratique fréquente consiste à prendre des photos du tableau ou du cahier afin de conserver rapidement une trace du cours. Cependant, ces captures restent brutes : elles ne sont pas classées, ne sont pas recherchables et ne sont pas exploitables directement pour la révision.

L'étudiant doit ensuite relire, recopier, résumer et préparer lui-même des questions d'entraînement, ce qui demande du temps et une grande rigueur. Les méthodes d'apprentissage actif, telles que les quiz et les flashcards, sont reconnues pour favoriser la mémorisation à long terme~\cite{ebbinghaus1885}. Pourtant, leur préparation reste manuelle et répétitive.

\subsection{Apport de l'intelligence artificielle}

Les avancées récentes dans le domaine de l'OCR, des modèles de vision et des grands modèles de langage ouvrent de nouvelles possibilités. Il devient envisageable de construire un pipeline entièrement automatisé, de l'image brute jusqu'au support de révision structuré, en combinant reconnaissance de texte, compréhension du contenu et génération de ressources pédagogiques.

\section{Problématique}

\begin{quote}
\textit{Comment concevoir une application mobile intelligente capable de transformer automatiquement des captures de notes académiques en ressources d'apprentissage structurées, interactives et personnalisées ?}
\end{quote}

Cette problématique soulève plusieurs défis techniques : la qualité variable des images capturées, la reconnaissance précise du texte et des formules mathématiques, la compréhension du contenu extrait, la génération de ressources pédagogiques pertinentes, ainsi que la protection des données personnelles de chaque utilisateur.

\section{Étude de l'existant}

Plusieurs outils permettent déjà de répondre partiellement à ce besoin.

\begin{itemize}[label=--]
    \item \textbf{Google Lens} extrait du texte à partir d'une image, mais ne propose pas de transformation pédagogique complète.
    \item \textbf{Quizlet} facilite la création et la révision de flashcards, mais la préparation du contenu reste manuelle.
    \item \textbf{Notion AI} et \textbf{ChatGPT} peuvent résumer ou expliquer un contenu, mais ne sont pas conçus comme une chaîne intégrée allant de la capture d'une image à la génération de supports de révision.
    \item \textbf{Microsoft OneNote} permet d'organiser des notes, mais avec peu d'automatisation IA et sans génération de quiz ni flashcards.
\end{itemize}

Ces solutions restent fragmentées. L'étudiant doit passer d'un outil à un autre : capturer l'image, extraire le texte, copier le contenu, demander un résumé, générer des questions, puis organiser les cartes de révision. Le projet AACA propose de centraliser toutes ces étapes dans une seule application mobile avec une expérience unifiée et fluide.

\section{Objectifs du projet}

\subsection{Objectifs fonctionnels}

Les objectifs fonctionnels couvrent l'ensemble de la chaîne de traitement :

\begin{itemize}[label=--]
    \item permettre la création et la connexion sécurisée des utilisateurs ;
    \item capturer une image depuis la caméra ou l'importer depuis la galerie ;
    \item prendre en charge un flux multi-photos pour les cours sur plusieurs pages ou tableaux ;
    \item prétraiter l'image afin d'améliorer la lisibilité ;
    \item extraire automatiquement le texte à l'aide d'un système OCR multi-moteur ;
    \item détecter et extraire les formules mathématiques sous forme LaTeX ;
    \item corriger et structurer le texte extrait ;
    \item identifier automatiquement la matière du contenu ;
    \item générer un résumé pédagogique adaptatif ;
    \item générer des quiz interactifs à choix multiple ;
    \item générer des flashcards pour la révision espacée ;
    \item sauvegarder les notes et ressources dans un espace personnel ;
    \item proposer un assistant questions/réponses sur les notes ;
    \item suivre la progression et proposer des recommandations personnalisées.
\end{itemize}

\subsection{Objectifs non fonctionnels}

Au-delà des fonctionnalités visibles, l'application doit répondre à des exigences de qualité :

\begin{itemize}[label=--]
    \item \textbf{Sécurité :} protéger l'accès aux ressources via une authentification robuste (JWT) et un contrôle de propriété strict.
    \item \textbf{Ergonomie :} proposer une interface mobile claire, intuitive et adaptée à un usage étudiant quotidien.
    \item \textbf{Performance :} réduire autant que possible le temps de traitement d'une image.
    \item \textbf{Extensibilité :} permettre l'ajout de nouveaux moteurs OCR, modèles LLM ou fonctionnalités pédagogiques.
    \item \textbf{Maintenabilité :} organiser le code en modules séparés et testables.
    \item \textbf{Compatibilité :} viser un fonctionnement sur Android, iOS et web via Expo.
    \item \textbf{Fiabilité :} gérer les erreurs de manière explicite (codes HTTP cohérents, indisponibilité MongoDB → HTTP 503).
\end{itemize}

\chapter{Conception et architecture du système}

\section{Introduction}

Ce chapitre décrit la conception générale de l'application AACA. Il présente l'architecture globale, les composants principaux, les diagrammes UML de conception, le modèle de données et les choix technologiques retenus.

\section{Architecture globale}

\subsection{Principe général}

AACA repose sur une architecture client-serveur à trois couches. L'application mobile constitue la couche de présentation : elle permet à l'utilisateur d'interagir avec le système, de capturer des images et de consulter ses ressources. Le backend FastAPI forme la couche métier : il reçoit les requêtes, vérifie l'identité de l'utilisateur, orchestre le pipeline de traitement et communique avec les services d'intelligence artificielle. Enfin, la couche de persistance assure le stockage des utilisateurs, des notes, des quiz, des flashcards et des images.

Cette séparation permet de maintenir une application mobile légère, tandis que les traitements coûteux — OCR, extraction LaTeX, génération LLM, indexation vectorielle — sont centralisés côté serveur.

\subsection{Couches de l'application}

L'architecture se décompose en trois grandes couches :

\begin{itemize}[label=--]
    \item \textbf{Couche présentation :} application mobile React Native/Expo avec les écrans d'authentification, d'accueil, de capture, de notes, d'étude et de profil. La navigation est gérée par Expo Router (navigation basée sur les fichiers). L'état global est centralisé dans quatre contextes React : \texttt{AuthContext}, \texttt{NotesContext}, \texttt{StudyContext} et \texttt{AppearanceContext}.

    \item \textbf{Couche métier :} API REST FastAPI exposant les routes sous le préfixe \texttt{/api/v1}. Les services backend organisent les responsabilités : pipeline de traitement, OCR, prétraitement image, extraction de formules, génération LLM, RAG, apprentissage adaptatif et gestion des sessions multi-photos.

    \item \textbf{Couche données :} MongoDB pour les données structurées (utilisateurs, notes, quiz, flashcards, sessions, résultats), GridFS pour le stockage des images, et ChromaDB pour l'index vectoriel de recherche sémantique.
\end{itemize}

\section{Pipeline de traitement}

Le pipeline de traitement constitue le cœur du système. Il transforme une image brute en contenu pédagogique structuré à travers les étapes suivantes :

\begin{enumerate}
    \item réception et validation de l'image (type MIME, taille maximale) ;
    \item prétraitement OpenCV : correction de perspective, amélioration du contraste et débruitage ;
    \item extraction du texte par le moteur OCR sélectionné ;
    \item extraction des formules mathématiques sous forme LaTeX (pix2tex) ;
    \item correction et structuration du texte par LLM ;
    \item classification automatique de la matière ;
    \item génération du résumé adaptatif ;
    \item génération du quiz à choix multiple ;
    \item génération des flashcards ;
    \item sauvegarde en MongoDB et stockage de l'image dans GridFS ;
    \item indexation sémantique dans ChromaDB pour le service RAG.
\end{enumerate}

Cette organisation modulaire facilite l'évolution du projet : il est possible de remplacer le moteur OCR, d'ajouter un nouveau fournisseur LLM ou d'améliorer la reconnaissance des formules sans réécrire l'ensemble.

\subsection{OCR multi-moteur}

Le service OCR supporte plusieurs moteurs configurables via la variable d'environnement \texttt{OCR\_ENGINE} :

\begin{itemize}[label=--]
    \item \textbf{PaddleOCR PP-OCRv5} : moteur par défaut, reconnu pour sa précision sur des textes denses ;
    \item \textbf{EasyOCR} : alternative multi-langue ;
    \item \textbf{Tesseract} : moteur open-source, disponible pour plusieurs langues (français, anglais, arabe, allemand) ;
    \item \textbf{OpenAI Vision} : utilisé en repli automatique lorsque le score de confiance de l'OCR principal est inférieur au seuil configuré (\texttt{OCR\_CONFIDENCE\_THRESHOLD}).
\end{itemize}

\subsection{Extraction de formules mathématiques}

Le service \texttt{latex\_service.py} s'appuie sur \textbf{pix2tex}, un modèle Transformer entraîné pour reconnaître des équations mathématiques dans des images et les convertir en code LaTeX. Cette fonctionnalité est particulièrement utile pour les cours de mathématiques, physique ou chimie.

\subsection{Flux multi-photos (CourseSession)}

Pour les cours qui s'étendent sur plusieurs pages ou tableaux, un flux de session multi-photos permet à l'étudiant de capturer séquentiellement plusieurs images, de corriger le texte extrait de chaque capture, puis de finaliser la session. La finalisation déclenche une fusion des textes par LLM, suivie de la génération du résumé, du quiz et des flashcards pour l'ensemble du cours.

\subsection{Recherche sémantique (RAG)}

En complément de MongoDB, le projet intègre une recherche sémantique. Le texte de chaque note est découpé en fragments, transformé en vecteurs numériques grâce au modèle \texttt{text-embedding-3-small} d'OpenAI, puis indexé dans ChromaDB par utilisateur. Cette approche permet à l'assistant questions/réponses de retrouver les passages les plus pertinents en réponse à une question, constituant ainsi une implémentation du paradigme RAG~\cite{lewis2020}.

\subsection{Algorithme SM-2 et répétition espacée}

La révision des flashcards repose sur l'algorithme SuperMemo 2 (SM-2)~\cite{wozniak1990}, implémenté dans le service \texttt{adaptive\_learning.py}. Après chaque révision, l'utilisateur indique le niveau de difficulté ressenti sur une échelle de 1 à 5. L'algorithme met à jour trois paramètres de la carte :

\begin{itemize}[label=--]
    \item \textbf{easiness\_factor} (facteur de facilité, initialisé à 2,5) : ajusté en fonction de la note ;
    \item \textbf{interval} (nombre de jours avant la prochaine révision) : calculé à partir du facteur de facilité et du nombre de répétitions ;
    \item \textbf{next\_review} : date de la prochaine révision planifiée.
\end{itemize}

L'endpoint \texttt{GET /flashcards/due} retourne les cartes dont la date \texttt{next\_review} est inférieure ou égale à l'instant présent, triées par urgence.

\section{Architecture de sécurité}

La sécurité repose sur plusieurs mécanismes complémentaires :

\begin{itemize}[label=--]
    \item \textbf{Authentification JWT :} à la connexion, le serveur génère un jeton d'accès (durée de vie : 30 minutes) et un jeton de rafraîchissement (durée de vie : 7 jours). Toutes les routes protégées exigent un jeton d'accès valide dans l'en-tête \texttt{Authorization: Bearer}.
    \item \textbf{Hachage des mots de passe :} les mots de passe sont hachés avec bcrypt avant tout stockage.
    \item \textbf{Contrôle de propriété :} chaque ressource (note, quiz, flashcard) n'est accessible qu'à son propriétaire. La vérification d'une flashcard passe systématiquement par la note parente pour confirmer l'identité de l'utilisateur.
    \item \textbf{CORS strict :} le backend utilise une liste blanche d'origines autorisées. En production, l'absence de la variable \texttt{CORS\_ORIGINS} lève une \texttt{ValueError}.
    \item \textbf{Limitation de débit :} les routes sensibles (authentification, traitement d'images) sont protégées par un rate limiter (3 à 20 requêtes par minute selon la route).
    \item \textbf{Gestion explicite des erreurs :} l'indisponibilité de MongoDB déclenche une exception \texttt{ServiceUnavailableError} mappée sur HTTP 503.
\end{itemize}

\subsection{Justification des choix principaux}

\begin{itemize}[label=--]
    \item \textbf{React Native / Expo :} le choix d'un framework multi-plateforme permet de couvrir Android et iOS avec une seule base de code. Expo simplifie l'accès à la caméra, aux permissions et au déploiement.
    \item \textbf{FastAPI :} sa gestion native de l'asynchronisme, la validation automatique par Pydantic v2 et la génération automatique de documentation Swagger en font un choix adapté à un backend orienté traitements longs.
    \item \textbf{MongoDB :} la flexibilité des documents JSON est particulièrement adaptée aux structures variables des notes académiques (avec ou sans formules, avec différents niveaux de structuration).
    \item \textbf{OCR multi-moteur :} la variabilité des conditions de capture (luminosité, angle, qualité) rend indispensable un mécanisme de fallback entre plusieurs moteurs OCR.
    \item \textbf{LLM multi-fournisseur :} la prise en charge de plusieurs fournisseurs (OpenAI, Google Gemini, Anthropic Claude) garantit la disponibilité du service même si un fournisseur est temporairement inaccessible.
\end{itemize}

La solution repose sur des technologies modernes et extensibles, adaptées à un projet combinant mobile, backend et intelligence artificielle.

\subsection{Flux de capture et correction OCR}

L'écran de capture suit un flux en plusieurs étapes. L'utilisateur prend une photo ou l'importe depuis sa galerie. L'application envoie l'image à la route \texttt{POST /process/ocr-only} pour obtenir le texte brut rapidement sans déclencher la génération IA. L'utilisateur peut alors corriger le texte reconnu avant de soumettre à \texttt{POST /notes/from-text}, qui déclenche la génération complète des ressources pédagogiques.

Pour la capture multi-photos, le flux passe par les routes de session : chaque photo est envoyée à \texttt{POST /sessions/\{id\}/captures/ocr}, qui retourne le texte extrait pour correction. La finalisation à \texttt{POST /sessions/\{id\}/finalize} déclenche la fusion et la génération en lot.

\section{Limites observées}

Même si le projet répond aux objectifs principaux, certaines limites doivent être mentionnées :

\begin{itemize}[label=--]
    \item la qualité de l'OCR dépend fortement de la netteté, de la luminosité et de l'angle de la photo ;
    \item la reconnaissance des formules mathématiques manuscrites reste perfectible pour les écritures complexes ou peu nettes ;
    \item la génération de résumé, quiz et flashcards dépend de la disponibilité des services LLM configurés ;
    \item le temps de traitement complet peut être plus long pour des images complexes ou des sessions multi-photos volumineuses ;
    \item l'application nécessite une connexion au backend pour tous les traitements : pas de mode hors ligne pour les nouvelles captures ;
    \item les statistiques de progression pourraient être enrichies avec des graphiques temporels plus détaillés.
\end{itemize}

\section{Perspectives d'amélioration}

\subsection{Amélioration de la reconnaissance}

\begin{itemize}[label=--]
    \item \textbf{Écriture manuscrite :} affiner les modèles OCR ou entraîner un modèle spécifique sur des données académiques manuscrites en français et en arabe.
    \item \textbf{Formules mathématiques :} le fine-tuning du modèle pix2tex sur des jeux de données de formules académiques manuscrites est une piste concrète, notamment via l'utilisation d'un environnement Colab pour l'entraînement.

\subsection{Fonctionnalités à intégrer}

\begin{itemize}[label=--]
    \item \textbf{Mode hors ligne partiel :} permettre la consultation des notes déjà traitées sans connexion au backend.
    \item \textbf{Export des notes :} export en PDF ou en Markdown pour une utilisation externe.
    \item \textbf{Partage de notes :} permettre à un étudiant de partager une note ou un deck de flashcards avec d'autres utilisateurs.
    \item \textbf{Transcription audio :} intégrer la transcription de cours enregistrés pour élargir les sources d'entrée.
\end{itemize}

\subsection{Amélioration du système RAG}

Le service RAG actuel répond à des questions sur une note spécifique. Une version plus avancée permettrait d'interroger l'ensemble des notes d'un utilisateur avec une recherche multi-documents, d'améliorer la qualité du découpage en fragments et d'optimiser les embeddings pour le domaine académique~\cite{lewis2020}.

\subsection{Amélioration de l'expérience utilisateur}

\begin{itemize}[label=--]
    \item enrichir le tableau de bord avec des graphiques de progression temporelle ;
    \item ajouter des notifications de rappel pour les flashcards dues ;
    \item proposer des recommandations de révision plus contextuelles basées sur l'historique détaillé.
\end{itemize}

\section{Conclusion}

Ce chapitre a présenté la réalisation concrète du projet AACA. Le backend FastAPI structuré en services, le frontend React Native avec ses écrans spécialisés, le pipeline de traitement multi-étapes et les tests automatisés montrent que la solution proposée répond aux objectifs initiaux. Malgré les limites inhérentes à la qualité variable des images et à la dépendance aux services LLM, le projet constitue une base solide pour un assistant cognitif académique complet.

\chapter*{Conclusion générale}
\addcontentsline{toc}{chapter}{Conclusion générale}

Le projet \textbf{AACA} démontre comment l'intelligence artificielle peut être mise au service de l'apprentissage étudiant de manière concrète et intégrée. En combinant une application mobile, un backend API modulaire, des moteurs OCR, l'extraction de formules mathématiques, des grands modèles de langage, un algorithme de répétition espacée et une recherche sémantique, le système permet de transformer une simple capture de cours en un ensemble cohérent de ressources pédagogiques.

Les objectifs principaux ont été atteints : capture ou import d'image, extraction de texte, correction OCR interactive, structuration du contenu, génération de résumé, création de quiz QCM, génération de flashcards avec planification SM-2, assistant questions/réponses sur les notes, flux multi-photos pour les cours sur plusieurs pages, et tableau de bord de suivi de progression. La sécurité a été traitée avec rigueur : authentification JWT, contrôle de propriété des ressources, CORS strict et gestion explicite des erreurs.

Ce travail a permis de mettre en pratique des compétences variées et complémentaires : développement mobile cross-platform, conception d'une API REST, bases de données NoSQL, traitement d'images, intégration de modèles d'IA et implémentation d'un algorithme d'apprentissage adaptatif.

Les limites identifiées — dépendance à la qualité de l'image, absence de mode hors ligne, reconnaissance imparfaite des formules manuscrites — ouvrent des perspectives d'amélioration concrètes. Le fine-tuning de modèles OCR et de reconnaissance de formules, l'enrichissement du pipeline RAG, et l'ajout d'un mode hors ligne constituent les axes prioritaires pour une version future. AACA constitue ainsi une base solide et extensible pour accompagner les étudiants dans une révision plus active, plus organisée et plus personnalisée.

\chapter{Guide d'installation}

\section{Backend}

\begin{enumerate}
    \item Se placer dans le dossier \texttt{backend/}.
    \item Créer et activer un environnement virtuel Python :
\begin{lstlisting}[language=bash]
python3 -m venv venv
source venv/bin/activate     # Linux / Mac
\end{lstlisting}
    \item Installer les dépendances :
\begin{lstlisting}[language=bash]
pip install -r requirements.txt
\end{lstlisting}
    \item Copier le fichier de configuration et renseigner les variables :
\begin{lstlisting}[language=bash]
cp .env.example .env
# Renseigner : SECRET_KEY, MONGODB_URL, OPENAI_API_KEY (ou autre LLM)
\end{lstlisting}
    \item Lancer MongoDB (option Docker) :
\begin{lstlisting}[language=bash]
docker run -d --name mongodb-aaca -p 27017:27017 mongo:7.0
\end{lstlisting}
    \item Démarrer le serveur :
\begin{lstlisting}[language=bash]
uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
\end{lstlisting}
    \item La documentation Swagger est disponible à \texttt{http://localhost:8000/docs}.
\end{enumerate}

\section{Frontend}

\begin{enumerate}
    \item Se placer dans le dossier \texttt{frontend/}.
    \item Installer les dépendances :
\begin{lstlisting}[language=bash]
npm install
\end{lstlisting}
    \item Configurer l'adresse de l'API dans \texttt{.env} :
\begin{lstlisting}
EXPO_PUBLIC_API_URL=http://ADRESSE_IP:8000/api/v1
\end{lstlisting}
    \item Lancer l'application :
\begin{lstlisting}[language=bash]
npx expo start
\end{lstlisting}
    \item Scanner le QR code avec Expo Go (téléphone physique) ou lancer sur un simulateur.
\end{enumerate}

\section{Route protégée avec vérification de propriété}

\begin{lstlisting}[language=Python]
async def _get_owned_note(note_id: str, current_user: str) -> dict:
    note = await mongodb_service.get_note(note_id)
    if not note or note["user_id"] != current_user:
        raise HTTPException(
            status_code=status.HTTP_404_NOT_FOUND,
            detail="Note not found",
        )
    return note

@router.get("/notes/{note_id}", response_model=Note)
async def get_note(
    note_id: str,
    current_user: str = Depends(get_current_user),
) -> Note:
    note = await _get_owned_note(note_id, current_user)
    return Note(**note)
\end{lstlisting}

\section{Calcul SM-2 et mise à jour de la flashcard}

\begin{lstlisting}[language=Python]
@router.post("/flashcards/{card_id}/review")
async def review_flashcard(
    card_id: str,
    review: FlashcardReview,
    current_user: str = Depends(get_current_user),
) -> dict:
    card = await mongodb_service.get_flashcard(card_id)
    await _get_owned_note(card["note_id"], current_user)  # ownership check

    sm2 = adaptive_learning.compute_sm2(card, review.difficulty_rating)
    await mongodb_service.update_flashcard(card_id, {
        "next_review": sm2["next_review"],
        "easiness_factor": sm2["easiness_factor"],
        "interval": sm2["interval"],
        "repetitions": sm2["repetitions"],
        "last_reviewed": review.reviewed_at,
    })
    return {"next_review": sm2["next_review"], "interval": sm2["interval"]}
\end{lstlisting}
